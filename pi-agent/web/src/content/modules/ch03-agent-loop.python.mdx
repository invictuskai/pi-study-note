## 一、引子：大模型的三种用法

### 模式 1：直接调用 —— "模型，回答我"

<Diagram file="/assets/diagrams/ch03-diagram-d47dd89d0526.svg" caption="模式 1：直接调用 —— &quot;模型，回答我&quot;" id="ch03-diagram-d47dd89d0526" layout="preserve" />

例如翻译或摘要。下面是通用伪代码，不是 pi SDK 的函数签名：

```python
# 通用调用示意，不是官方 Python SDK
response = await llm.chat(messages=[
    {"role": "system", "content": "你是一个翻译助手"},
    {"role": "user", "content": "把这段文字翻译成中文"},
])
print(response.content)
```

一次请求得到一次回复。提示词影响质量，但不保证结果正确。

### 模式 2：Workflow —— "模型，你先做第一步，我检查一下，再做第二步"

<Diagram file="/assets/diagrams/ch03-diagram-8b86b64fbc73.svg" caption="模式 2：Workflow —— &quot;模型，你先做第一步，我检查一下，再做第二步&quot;" id="ch03-diagram-8b86b64fbc73" layout="preserve" />

步骤及分支由应用代码预先编排。每一步模型只负责其中一部分，代码决定进入哪一步。

### 模式 3：Agent Loop —— "模型，你自己决定怎么做"

<Diagram file="/assets/diagrams/ch03-diagram-faae1b02c2a1.svg" caption="模式 3：Agent Loop —— &quot;模型，你自己决定怎么做&quot;" id="ch03-diagram-faae1b02c2a1" layout="preserve" />

模型选择要请求的工具及参数，程序负责验证、执行和调度。**“我接下来会读文件”只是一句话；只有结构化的 `toolCall` 才进入工具执行路径。**

| 维度 | 直接调用 | Workflow | Agent Loop |
|---|---|---|---|
| 下一步由谁决定 | 调用方 | 预设代码 | 模型输出与运行时规则共同决定 |
| 模型调用次数 | 通常一次 | 由流程决定 | 由工具、队列、回调等决定 |
| 核心工作 | 组织输入 | 设计步骤与检查 | 定义工具、权限、上下文和续跑规则 |

Agent 也可以有验收逻辑、预算限制和预设子流程。这些机制并不与 Agent Loop 冲突。

## 二、先搞清楚几个概念：Trace、Turn

### Trace（本章指一次完整运行）

本章用 Trace 指 `agent_start` 到 `agent_end` 的事件范围，不把它当成一个名为 `Trace` 的核心类型。一轮运行包含一个或多个 Turn。

<Diagram file="/assets/diagrams/ch03-diagram-115d7522dbd0.svg" caption="Trace（本章指一次完整运行）" id="ch03-diagram-115d7522dbd0" layout="preserve" />

`agent_end` 表示不再产生本次循环的后续事件。使用 `Agent` 类时，订阅者仍可能正在处理这个事件；`prompt()` / `waitForIdle()` 要等这些异步订阅者完成后才结束等待。

### Turn（一个轮次）

在这里，一个 Turn 是**一次 `streamAssistantResponse` 调用及其工具结果处理**，由 `turn_start` / `turn_end` 包裹。一次逻辑模型调用内部可能有 provider 的重试，不能据此认定只有一次 HTTP 请求。

一条 assistant 消息请求了 read、grep、find，这一批工具属于同一个 Turn。拿着结果再调用模型，才是下一 Turn。

<Diagram file="/assets/diagrams/ch03-diagram-a4bb2dd21907.svg" caption="Turn（一个轮次）" id="ch03-diagram-a4bb2dd21907" layout="preserve" />

首轮 `turn_start` 由 `runAgentLoop` / `runAgentLoopContinue` 发出。后续轮次通过 `lastCompletedTurn` 判断；该变量跨外层循环保留，所以 follow-up 重启内层时也会产生新的 `turn_start`。当前实现不是每次外层循环重新设置 `firstTurn`。

<Diagram file="/assets/260702-ch03-trace-turn-nesting.svg" caption="Trace 与 Turn 的嵌套结构" id="260702-ch03-trace-turn-nesting" />

## 三、全景：一条消息的旅程，以及循环怎么转

### 流程全景

用户说“帮我读一下 src/main.ts”，没有额外回调决定或排队输入时：

<Diagram file="/assets/diagrams/ch03-diagram-060bb5c17c0a.svg" caption="流程全景" id="ch03-diagram-060bb5c17c0a" layout="preserve" />

`hasMoreToolCalls` 的名字容易误导。它不表示已经知道下一轮还会有工具，也不是“还有工具没执行”。它表示：**本轮工具处理是否要求再调用一次模型。**

### stopReason：本次生成为什么结束

`stopReason` 是 pi 的统一分类，由 API 实现把供应商响应或本地异常转换而来；不同 API 的原始字段和值不必相同。

| 分类 | 含义 | Loop 中的作用 |
|---|---|---|
| `stop` | 生成正常结束 | 仍检查实际 content，不直接据此退出 |
| `toolUse` | 生成了工具使用请求 | 仍检查实际 toolCall 块，不只认这个标签 |
| `length` | 输出被长度限制截断 | 含 toolCall 时拒绝执行，生成错误结果 |
| `error` | 调用失败 | 收尾后硬退出，不检查队列 |
| `aborted` | 调用被取消 | 收尾后硬退出，不检查队列 |
| `pending` | 响应尚未最终完成的状态 | 通常见于流式 partial，不是正常终止事件的 reason |
| `deferred` | 供应商返回延后完成的请求句柄 | 这个旧式 Loop 没有专门轮询分支；后续处理取决于调用方 |

`StopReason` 当前包含七种值，不能再把旧版常见的五种当成完整类型。`AssistantMessage.endTurn` 还可保留供应商的结束提示，但该字段目前不参与这里的控制流。

因此，“模型这次回复结束”“工具执行结束”“整个运行结束”是三件不同的事。

### 工具触发的续跑规则

以下为 `runLoop` 工具分支的节选；此前已经排除了 `error` / `aborted`：

```python
# 教学改写：先前已排除 error / aborted
calls = [c for c in message.content if c.type == "toolCall"]
tool_results = []
has_more_tool_calls = False
if calls:
    if message.stop_reason == "length":
        batch = await fail_tool_calls_from_truncated_message(calls, emit)
    else:
        batch = await execute_tool_calls(context, message, config, signal, emit)
    tool_results.extend(batch.messages)
    has_more_tool_calls = not batch.terminate
    for result in tool_results:
        context.messages.append(result)
        new_messages.append(result)
```

每轮先把标志清为 false，再由这一轮实际结果决定是否续跑。进入外层循环时设为 true，则是为了保证至少进入一次模型调用，并不代表事先已有工具请求。

**截断时为什么不执行？** 例如模型生成一个写文件调用，参数恰好被 token 上限切断。即使 JSON 修复器能把残缺参数解析成合法对象，也不能证明内容完整。当前实现拒绝本条消息中的所有工具调用，返回带 `isError: true` 的工具结果，让模型重新生成完整参数；这个失败批次的 `terminate` 为 false。

反过来，`length` 且没有工具调用时，循环没有内建的“自动续写”分支。后续是否继续，还要看队列和回调。

### terminate：取消工具触发的自动续跑，而不是强制退出

当前汇总逻辑是：

```python
# TS 的 every 对应 Python 的 all；显式检查非空，避免 all([]) 为 True
return bool(finalized_calls) and all(
    call.result.terminate is True for call in finalized_calls
)
```

| 本批最终工具结果的 terminate | 批次 terminate |
|---|---|
| `[true]` | true |
| `[true, true]` | true |
| `[true, false]` | false |
| `[true, undefined]` | false |
| `[undefined]` | false |

这是 `every`，不是 `some`。结果可以来自工具本身、拦截调用的 `beforeToolCall` 或覆盖结果的 `afterToolCall`。

这个提示不取消本批其他工具，也不直接 `return`。它只把 `hasMoreToolCalls` 置为 false；steering、follow-up 或 `finishTurn` 的继续决定仍可能让运行续跑。

### 循环的所有正常调度出口

<Diagram file="/assets/260702-ch03-stopreason-flowchart.svg" caption="模型结果、工具与队列共同决定续跑" id="260702-ch03-stopreason-flowchart" />

| 路径 | 行为 |
|---|---|
| assistant 为 `error` / `aborted` | 调用 `finishTurn` 收尾但忽略决定，发送 turn_end、agent_end，return |
| 正常轮次 `finishTurn` 返回 `{ action: "end" }` | 发送 turn_end、agent_end，return；不再检查队列 |
| 工具要求续跑或存在 steering | 继续内层循环 |
| 内层退出但有 follow-up | 将其置为 pending，继续外层循环 |
| 没有自然续跑原因，但 `finishTurn` 要求 continue | 继续外层，用已有上下文再调一次模型 |
| 上述续跑原因全部没有 | break 外层，发送 agent_end |

这里说的是 `runLoop` 的调度路径。回调自身抛出异常会向调用方传播；`Agent` 类另有 `runWithLifecycle` / `handleRunFailure` 处理运行异常，不能把它与 assistant 已返回的 `stopReason` 分支混为一谈。

**“没有工具，那就当你完成了”只是最简模型。** 更准确的说法是：模型影响下一步要做什么，程序判断是否存在下一次调用的理由。`agent_end` 不证明用户目标已达成；例如模型只说“我马上读文件”却没有工具调用，也没有其他续跑要求，运行一样会停。

## 四、源码详解：基础 Loop 与产品叠加设计

这些队列和钩子实现在 `pi-agent-core`，不是 coding-agent 独有。coding-agent 可以使用这些能力；当前仓库也有 `packages/agent/src/harness/` 等运行实现，本章只追踪 `agent-loop.ts` 这条路径，不能把它当成所有 runtime 的唯一驱动器。

### 最简 Loop：先看正常路径

下面仅演示正常、未截断、无终止提示的工具往返，不是完整生产实现：

```python
# 仅正常路径的教学伪代码；未实现错误、截断、权限和队列
async def simple_loop(messages, model, tools):
    while True:
        response = await call_model(model, messages, tools)
        messages.append(response)
        calls = [c for c in response.content if c.type == "toolCall"]
        if not calls:
            return messages
        for call in calls:
            messages.append(await execute_tool(call))
```

完整实现必须再处理截断、取消、错误、权限、消息队列和资源限制。简化循环是学习模型，不是所有 Agent 必须采用的唯一架构。

### 4.1 入口：runAgentLoop() 收到了什么

`Agent.prompt()` → `runPromptMessages()` → `runAgentLoop()`。当前签名如下：

```python
# 对应 runAgentLoop 的参数形状，不是可导入的 Python SDK
async def run_agent_loop(prompts, context, config, emit, signal, stream_fn):
    # signal 可传 None，stream_fn 由调用方提供
    ...
```

`AgentContext` 包含消息历史和可执行工具。系统提示词已经属于消息历史，不再是 context 的独立 `systemPrompt` 字段：

```python
# 数据形状示意；read_tool / bash_tool 代表已定义的工具
context = {
    "messages": [
        {"role": "system", "content": "你是代码助手", "timestamp": now_ms},
        {"role": "user", "content": "帮我读一下 src/main.ts", "timestamp": now_ms},
    ],
    "tools": [read_tool, bash_tool],
}
```

`createContextSnapshot()` 对 messages、tools 数组做浅拷贝，元素并非深拷贝。Loop 发出的事件又经 `Agent.processEvents()` 更新 Agent 状态，因此不能说运行完全不影响原始状态。

入口先调用 `declareToolChanges(context, prompts)`：将当前可执行工具集合相对于历史声明的变化写成 system 消息。然后建立 `newMessages`、合并上下文，发送 agent_start、首轮 turn_start 和初始消息事件，最后进入 `runLoop`。

主要可选回调：

| 回调 | 用途 |
|---|---|
| `prepareNextTurn` | 已选定后续轮次时，更新 context、messages、model、thinkingLevel |
| `prepareRequest` | 每次模型请求前更新 context、model、thinkingLevel，包括首轮 |
| `transformContext` | 转换发送给模型的消息数组 |
| `convertToLlm` | 将 AgentMessage 转成 Message |
| `finishTurn` | 轮次结果完成后收尾，并可决定 end / continue |
| `getSteeringMessages` / `getFollowUpMessages` | 拉取排队输入 |
| `beforeToolCall` / `afterToolCall` | 工具预检和结果处理 |

### 4.2 runLoop() 的骨架：内层和外层分别负责什么

下面是调度顺序示意。`处理本轮` 等中文步骤不是可调用函数；具体实现见后续小节。

```text
lastCompletedTurn = undefined
explicitContinuation = false
pendingMessages = 首次取 steering

外层 while true：
  hasMoreToolCalls = true
  内层 while hasMoreToolCalls 或 pending 非空：
    如果已有 lastCompletedTurn：
      prepareNextTurn，应用返回的更新和准备消息
      若 pending 为空，补取准备期间到达的 steering
      turn_start
    声明工具变化，注入 preparedMessages 和 pendingMessages
    清空 pending
    prepareRequest，应用更新
    调模型
    若 error / aborted：finishTurn 收尾，turn_end，agent_end，return
    处理工具调用，更新 hasMoreToolCalls 和历史
    保存 lastCompletedTurn
    finishTurn → turn_end
    若决定 end：agent_end，return
    记录是否显式 continue
    取 steering
    若工具或 steering 已要求下一轮，消耗显式 continue 决定

  取 follow-up
  若有：消耗显式 continue 决定，设为 pending，continue 外层
  若仍有显式 continue：清除标志，continue 外层
  break 外层

agent_end
```

内层照顾工具结果和及时输入；外层在准备停下时处理 follow-up 或没有新输入的显式续跑。`lastCompletedTurn` 不在外层顶部清空。

### 4.3 steering 消息注入

用户在运行时补充“也检查一下测试文件”，消息先进入 steering 队列，不会中断本轮已经开始的模型响应或工具批次。

读取时机是：

1. `runLoop` 启动时。
2. 正常轮次完成且没有被 `finishTurn` 结束后。
3. 后续轮次 `prepareNextTurn` 完成后，如果先前没有取到 pending，再补取一次。

第三项解决准备工作较慢时新消息到达的问题。若已经取到消息则不重复取，避免 one-at-a-time 模式一轮意外消费两条。`prepareRequest` 期间到达的消息不会在它结束时额外补取，要等下一个正常检查点。

注入时不只有 steering，还包括 `prepareNextTurn` 返回的消息：

```python
# 教学改写：合并准备消息和排队输入，再声明工具变化
for message in declare_tool_changes(context, prepared_messages + pending_messages):
    await emit({"type": "message_start", "message": message})
    await emit({"type": "message_end", "message": message})
    context.messages.append(message)
    new_messages.append(message)
pending_messages = []
```

### 4.4 streamAssistantResponse()：调用模型和处理流

#### 阶段 A：上下文预处理

```python
messages = context.messages
if config.transform_context:
    messages = await config.transform_context(messages, signal)
```

返回的是本次请求使用的消息。这个钩子本身不意味着原始会话文件已经被压缩或改写。

#### 阶段 B：转换消息

```python
# 概念示意：TS 可接受同步或异步转换器，此处假设异步转换器
llm_messages = await config.convert_to_llm(messages)
```

`Agent` 默认转换器保留四种标准角色：

```python
def default_convert_to_llm(messages):
    return [m for m in messages
            if m.role in ("system", "user", "assistant", "toolResult")]
```

默认转换器会过滤自定义角色。应用可以提供自己的转换器，把摘要、用户执行的 Bash 记录等转换成模型消息。不能把“默认过滤”误解为 coding-agent 一定丢弃这些信息。

#### 阶段 C：规范化 transcript 并调用注入的 stream 函数

```python
# 教学改写；此处把 config.options 作为流式选项字典
llm_context = normalize_context({"messages": llm_messages})
key = await config.get_api_key(config.model.provider) if config.get_api_key else None
response = await stream_function(config.model, llm_context, {
    **config.options,
    "api_key": key or config.api_key,
    "signal": signal,
})
```

当前传递的是以消息为中心的上下文。system 消息保存系统提示和工具声明，运行时的 `context.tools` 则保存能实际执行的工具。不要再照抄旧版的 `{ systemPrompt, messages, tools }` 构造过程。

`AgentOptions.streamFn` 当前是必需参数。常见用法是把配置好 provider 的 models 实例方法绑定后注入；旧全局 API 不应从 `pi-ai` 主入口直接导入。

**这与 prompt cache 有什么关系？** 缓存看的是供应商请求的内容和服务端策略，不是 JavaScript 对象身份。创建新的 context wrapper 不等于缓存失效，复用同一个 tools 数组也不保证命中。provider 负责把 transcript 转换成供应商协议并应用缓存设置；具体标记位置、有效期、最小长度等不属于这个循环的保证。下一章再沿 API 实现追踪。

#### 阶段 D：流式响应原地替换

```text
start：把 partial assistant 消息 push 到 Loop 的 context
text/thinking/toolcall 更新：替换 context 的最后一个元素，发送 message_update
done/error：用最终消息替换，发送 message_end，返回 AssistantMessage
```

这样只保留一条不断增长的 assistant 消息，不会把每一个 token 都存成独立消息。源码还处理未收到 start 或流结束后的兜底情况；不能无条件假设最后一个数组元素总是待替换的 assistant。

UI 通过事件读取进度，不是直接观察这个局部数组。`Agent` 在更新阶段维护 `streamingMessage`，到 `message_end` 时才追加最终消息到自身历史。

### 4.5 检查 stopReason：硬停止先于工具

```python
if message.stop_reason in ("error", "aborted"):
    last_completed_turn = {
        "message": message, "tool_results": [],
        "context": context, "new_messages": new_messages,
    }
    if config.finish_turn:
        await config.finish_turn(last_completed_turn, signal)  # 忽略决定
    await emit({"type": "turn_end", "message": message, "tool_results": []})
    await emit({"type": "agent_end", "messages": new_messages})
    return
```

即使消息含有工具块也不执行。`finishTurn` 用于收尾，但它返回 continue 也不会覆盖这个硬退出。

工具执行抛错是另一回事：通常被捕获并包装成 `isError: true` 的工具结果，让下一轮模型处理。**工具失败不等于 assistant 的 stopReason 为 error。**

### 4.6 executeToolCalls()：并行与串行

只有未被 `length` 拒绝的调用才进入真正执行函数。选择规则为：

```python
# 参数省略，只演示调度分支
if config.tool_execution == "sequential" or has_sequential_tool_call:
    return await execute_tool_calls_sequential(...)
return await execute_tool_calls_parallel(...)
```

任一目标工具声明 `executionMode: "sequential"`，整批就采用串行。否则默认并行。

<Diagram file="/assets/diagrams/ch03-diagram-f73513965ed1.svg" caption="4.6 executeToolCalls()：并行与串行" id="ch03-diagram-f73513965ed1" layout="preserve" />

预检顺序执行是当前实现的选择，不意味着权限校验在原理上不能并行。**B 被拦截不自动拦截 C**；只有取消信号等另行控制后续处理。并发部分也不仅是 `tool.execute`，其 after hook 和结束通知同样属于各自异步任务。

工具参数准备、schema 验证、before hook、execute、after hook 的五步管道，见第 5 章。

### 4.7 finishTurn、turn_end 与下一轮准备

正常轮次先完成所有工具结果，再调用 `finishTurn`，然后发送 `turn_end`：

```python
# 教学改写，此处假设钩子为异步函数，决定为字典
last_completed_turn = {
    "message": message, "tool_results": tool_results,
    "context": context, "new_messages": new_messages,
}
decision = (await config.finish_turn(last_completed_turn, signal)
            if config.finish_turn else None)
await emit({"type": "turn_end", "message": message, "tool_results": tool_results})
if decision and decision["action"] == "end":
    await emit({"type": "agent_end", "messages": new_messages})
    return
explicit_continuation = bool(decision and decision["action"] == "continue")
pending_messages = (await config.get_steering_messages()
                    if config.get_steering_messages else [])
if has_more_tool_calls or pending_messages:
    explicit_continuation = False
```

- 返回 `undefined`：按正常工具/消息调度运行。
- 返回 `{ action: "end" }`：当前轮结束后停止，不再取队列。
- 返回 `{ action: "continue" }`：保证下一次逻辑模型请求；若工具或队列本就触发下一轮，不再额外加一轮。

每轮都会再次调用这个回调，永远返回 continue 就可能无限运行。当前接口是 `finishTurn`；旧版 `shouldStopAfterTurn` 不能直接照搬。

`prepareNextTurn` 则只在**已经选定下一轮后**执行，位于后续 `turn_start` 之前。它能返回 context、messages、model、thinkingLevel 的更新，例如在读完多个文件后切到另一个模型。若自然停止且没有后续输入，就不会为一个不存在的下一轮运行它。

### 4.8 回到内层循环顶部

```python
while has_more_tool_calls or pending_messages:
    ...
```

| 工具要求再调模型 | pending 非空 | 结果 |
|---|---|---|
| 是 | 否 | 下一轮 |
| 否 | 是 | 下一轮 |
| 是 | 是 | 下一轮，两个理由合并 |
| 否 | 否 | 仅退出内层，还未结束整个函数 |

`pendingMessages` 是待注入的新输入，不是整个聊天历史。它也可以来自外层选中的 follow-up。

### 4.9 外层循环：follow-up 和显式 continue

```python
# 位于外层 while True 内，内层循环已经退出
follow_up = (await config.get_follow_up_messages()
             if config.get_follow_up_messages else [])
if follow_up:
    explicit_continuation = False
    pending_messages = follow_up
    continue
if explicit_continuation:
    explicit_continuation = False
    continue
break
```

有 follow-up，就在同一次运行内注入它。没有 follow-up 但尚有显式 continue，就用现有上下文再请求一次。两者都没有才真正退出外层。

因此，`terminate: true` 只是取消一个续跑理由；内层条件为 false 只是结束一层循环；硬停止分支的 `return` 才直接离开整个函数。

### 4.10 steering vs followUp：两种输入优先级

| 维度 | steering | followUp |
|---|---|---|
| 读取时机 | 启动时、正常轮次末尾；后续准备完成后按条件补取 | 内层自然退出后 |
| 生效位置 | 下一轮输入，不插入当前工具批次中间 | 准备结束当前工作时启动后续轮次 |
| 示例 | “先别改文件，解释一下” | “当前分析结束后，再写摘要” |

两种队列的 one-at-a-time / all 模式由 `PendingMessageQueue` 控制。它们都不等价于 `abort()`。

## 五、总结：Loop 的四条核心设计

1. **工具往返**：模型输出请求，程序处理工具，下一轮模型观察结果。
2. **运行结束不等于任务验收**：stopReason、实际工具块、批次结果、消息队列和 finishTurn 共同参与调度。
3. **内层与外层分工**：内层处理工具/及时输入，外层处理 follow-up 和显式续跑。
4. **准备、收尾各有边界**：prepareNextTurn 在已选定的后续轮次前；prepareRequest 在每次请求前；finishTurn 在 turn_end 前。
