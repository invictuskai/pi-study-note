第 3 章的 Loop 调用注入的 `streamFunction`。它可以绑定到 models 实例：

```typescript
import { createModels } from "@earendil-works/pi-ai";
import { anthropicProvider } from "@earendil-works/pi-ai/providers/anthropic";
import { Agent } from "@earendil-works/pi-agent-core";

const models = createModels();
models.setProvider(anthropicProvider());
const model = models.getModel("anthropic", "claude-sonnet-4-6");
if (!model) throw new Error("Model not found");

const agent = new Agent({
  initialState: { model, systemPrompt: "你是一个助手。" },
  streamFn: models.streamSimple.bind(models),
});
// 配置好认证后再调用 await agent.prompt("你好")，会产生真实模型请求。
```

一行调用的简洁来自职责分离，不是“所有 API 在启动时自动注册成一个全局表”。

## 一、问题：同一段对话，不同 API 要翻译成不同格式

Pi 的统一用户消息是：

```typescript
{ role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }
```

发送到供应商时，API 实现要转换消息、图片、工具 schema、工具结果以及思考内容。例如：

| API | 用户文本的常见形状 | 工具结果 |
|---|---|---|
| Anthropic Messages | `content` 可以是字符串，也可以是带 type 的块数组 | user 消息内的 tool_result 块 |
| OpenAI Chat Completions | user 消息，content 为字符串或块数组 | role 为 tool 的消息 |
| OpenAI Responses | input 中的消息项 | function_call_output 等输入项 |
| Google | content 使用 parts 数组 | functionResponse |
| Bedrock Converse | content 数组内使用 text 字段 | toolResult 块 |

这里对比的是**协议**，不是供应商一一对应的私有方言。一个 Provider 可以使用多个 API，多个 Provider 也可以共用同一个 API。当前内建 `openaiProvider()` 使用 `openai-responses`，不能把 Chat Completions 的 `role: "tool"` 当成所有 OpenAI 请求的格式。

<Diagram file="/assets/260702-ch04-provider-formats.svg" caption="不同 API 的消息格式示意" id="260702-ch04-provider-formats" />

差异还包括流式事件、认证、思考参数、缓存、工具约束和取消行为。统一接口减少上层分支，但不能消除真实能力差异。

## 二、解法：Models、Provider 与 API 实现

### 第一层：Models 集合负责找到供应商并应用认证

`createModels()` 创建独立集合；`setProvider()` 按 provider.id 注册或替换。它不是默认包含全部供应商的全局单例。

```text
models.streamSimple(model, context, options)
  → normalizeContext(context)
  → lazyStream 返回事件流，异步准备请求
  → 按 model.provider 找到 Provider
  → applyAuth：解析认证、合并 headers/env/请求选项
  → provider.streamSimple(requestModel, transcript, requestOptions)
```

`ModelsImpl.requireProvider` 查的是 `model.provider`。`model.api` 决定协议，但不是这一层查 provider 的 key。

Models 也提供模型查询和认证操作：

- `getModel` / `getModels`：同步读取最后已知目录，不自动探测网络。
- `refresh`：显式刷新动态目录，返回各 provider 的错误及取消状态。
- `getAvailable`：异步检查认证配置并应用 provider 的模型过滤规则，不是远程服务健康检查。
- `getAuth`：解析认证，必要时刷新 OAuth；只想检查配置时还可用 `checkAuth`。

### 第二层：Provider 组合目录、认证和协议实现

以 `providers/anthropic.ts` 为例，它调用 `createProvider`，提供 id、名称、模型目录、API-key/OAuth 认证和 `anthropicMessagesApi()`。

```text
Provider
  id / name / baseUrl
  auth                       认证策略
  getModels()                已知模型目录
  stream / streamSimple      请求行为
  可选动态目录、延后请求等能力
```

`createProvider` 可以接收一个 API 实现，也可以接收按 `model.api` 分类的实现映射。只有在后一种情况下，这一层才需要再按 API 分派。

### 第三层：API 实现翻译请求与响应

`packages/ai/src/api/` 中的实现负责协议转换。`*.lazy.ts` 包装器延后加载具体实现；provider 工厂引入自己的目录和包装器，不等于立即加载所有 SDK。

| 导入路径 | 内容 |
|---|---|
| `@earendil-works/pi-ai` | 核心类型、集合、工具函数等，不加载所有内建目录 |
| `.../providers/anthropic` | 该 provider 工厂和目录 |
| `.../providers/all` | 显式取得全部内建 provider / 目录 |
| `.../api/anthropic-messages` | 直接加载具体 API 实现 |
| `.../compat` | 旧全局接口与注册表 |

<Diagram file="/assets/260702-ch04-translation-company.svg" caption="Models、Provider 与 API 实现" id="260702-ch04-translation-company" />

事件协议连接这些层，并不是请求必须经过的另一个“执行器”。

### StreamFunction：明确上下文边界

当前 API 实现接收的是 `TranscriptContext`：

```typescript
export type StreamFunction<
  TApi extends Api = Api,
  TOptions extends StreamOptions = StreamOptions,
> = (
  model: Model<TApi>,
  context: TranscriptContext,
  options?: TOptions,
) => AssistantMessageEventStream;
```

公开的 `models.stream*()` 接受 `Context`，仍支持 systemPrompt/tools 便捷字段；`normalizeContext` 把它们折入开头的 system 消息。**到了 Provider / API 层只有 transcript.messages，不能再读 context.systemPrompt 或 context.tools。**

直接调用 API 实现绕过 Models 的认证解析，应自行传入规范化上下文和认证。直接 `streamSimple` 缺少认证时可能同步抛错；集合中的认证/延迟加载失败则由 `lazyStream` 转为流里的 error。不能笼统承诺任何入口都永不抛错。

## 三、统一事件协议：12 种事件，但不是每个事件都有 partial

```text
start
text_start → text_delta* → text_end
thinking_start → thinking_delta* → thinking_end
toolcall_start → toolcall_delta* → toolcall_end
done(reason: stop / length / toolUse / deferred)
或 error(reason: error / aborted)
```

上述三类内容块可交错，不能假设一定先完成思考、再完成文本、最后才生成工具。使用 `contentIndex` 区分内容块。

- 非终止事件携带 `partial`，它是**共享、可继续变化的对象**，不是事件发生时的不可变快照。
- `done` 携带 `message`，`error` 携带 `error`，不是 partial。
- 正常流要求先 start；请求准备失败允许直接 error，不先发 start。
- `toolcall_end` 不表示工具已执行，也不表示参数已通过 schema 验证。
- `StopReason` 当前有 pending、stop、length、toolUse、error、aborted、deferred 七种值；pending 用于尚未确定结束原因的部分消息。

消费示例（models、model、context 已配置）：

```typescript
const stream = models.streamSimple(model, context, { reasoning: "high" });
for await (const event of stream) {
  switch (event.type) {
    case "text_delta":
      process.stdout.write(event.delta);
      break;
    case "toolcall_end":
      console.log("工具请求，不是执行结果：", event.toolCall.name);
      break;
    case "done":
      console.log("本次请求结束：", event.reason);
      break;
    case "error":
      console.error(event.reason, event.error.errorMessage);
      break;
  }
}
const message = await stream.result();
```

`message` 是否需要继续处理，属于第 3 章的循环规则，不由 done 事件直接证明任务完成。

## 四、怎么接入新模型：先判断是否已有兼容协议

### 已兼容的 HTTP 服务：复用 API 实现

不是每接入一个模型都要写“翻译器”。例如兼容 OpenAI Chat Completions 的企业网关，可以组合现成实现：

```typescript
import { createModels, createProvider, envApiKeyAuth, type Model } from "@earendil-works/pi-ai";
import { openAICompletionsApi } from "@earendil-works/pi-ai/api/openai-completions.lazy";

const gatewayModel: Model<"openai-completions"> = {
  id: "your-model-id",                 // 替换为网关真实模型 ID
  name: "Enterprise model",
  api: "openai-completions",
  provider: "enterprise",
  baseUrl: "https://gateway.example.com/v1", // 替换为实际地址
  reasoning: false,
  input: ["text"],
  cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
  contextWindow: 32768,                // 按服务实际能力填写
  maxTokens: 4096,
};
const models = createModels();
models.setProvider(createProvider({
  id: "enterprise",
  auth: { apiKey: envApiKeyAuth("Enterprise key", ["ENTERPRISE_API_KEY"]) },
  models: [gatewayModel],
  api: openAICompletionsApi(),
}));
```

这里零价格仅为示例占位，不代表服务免费。上下文窗口、思考支持、工具/图片能力和 compat 参数必须按实际服务验证。

### 新协议：实现 ProviderStreams 并测试完整链路

只有协议不兼容时，才实现 stream / streamSimple 等方法，转换输入、输出事件、usage、终止原因和错误，再通过 `createProvider` + `models.setProvider` 组合。

这不等于“写完一次永不修改”，也不保证会话、压缩、跨模型历史自然兼容。至少要验证工具调用/结果、取消、截断、空响应、上下文溢出、认证和历史重放。加入 pi 内建 provider 还涉及目录生成、类型、打包导出和 coding-agent 接入。

旧 `registerApiProvider` 只属于 compat 路线，不是当前 Models 实例的注册 API。

## 五、进阶：翻译器内部、思考和缓存

### 五步骨架是概念模型，不是每个文件的固定结构

```text
准备认证和客户端 → 构建供应商请求 → 发送请求 → 转换流式响应 → 发终止事件
```

<Diagram file="/assets/260702-ch04-translator-5-steps.svg" caption="API 实现的概念性五步骨架" id="260702-ch04-translator-5-steps" />

Anthropic 当前实际调用 `client.beta.messages.create(...).asResponse()`：**它使用官方 SDK 发请求，同时自行解码返回的 SSE**。源码包含 `iterateSseMessages`、`iterateAnthropicEvents` 和 JSON 修复处理，不能说“Anthropic 没有成熟 SDK 所以手写全部传输”。

其事件转换包括：

```text
content_block_start(text)     → text_start
content_block_delta(text)     → text_delta
content_block_start(tool_use) → toolcall_start
input_json_delta             → toolcall_delta
content_block_stop           → 对应的 *_end
message_delta                → 更新 usage / rawStopReason / stopReason
响应流完整结束并验证状态        → done，失败则 error
```

`message_delta` 不直接等于 done。若有 message_start 却没看到 message_stop，当前实现报错；end_turn 映射为 stop，tool_use 映射为 toolUse，max_tokens 映射为 length，refusal 等还可能映射为 error。

### stream 与 streamSimple 的区别

两个 **Models 方法** 都解析认证并调用 provider。差别主要在选项：

- `stream` 接受具体 API 的完整参数，例如 Anthropic 的 thinkingBudgetTokens、effort。
- `streamSimple` 接受统一的 reasoning 等选项，再由具体实现映射。

不是 Models.streamSimple 先统一执行一套 clamp，再调用 Models.stream。当前是两条分别委派给 provider 的路径；模型能力回退与具体参数映射也不是同一个函数。

### 思考级别：包含 max，且不等于固定 token 数

AI 层类型与 Agent 层类型要分清：

```typescript
// pi-ai
 type ThinkingLevel = "minimal" | "low" | "medium" | "high" | "xhigh" | "max";
 type ModelThinkingLevel = "off" | ThinkingLevel;
// pi-agent-core 的 ThinkingLevel 还包含 "off"。
```

`thinkingLevelMap` 是可选映射，不是每个 Model 必有的表。标准级别缺失通常使用默认值，null 表示不支持；xhigh/max 要显式声明才算支持。`getSupportedThinkingLevels` 查询能力，`clampThinkingLevel` 先向上找可用级别，再向下找；这只是回退算法，不代表“思考越多越安全”。

`simple-options.ts` 为采用 token 预算的路径定义默认值：minimal 1024、low 2048、medium 8192、high 16384。`thinkingBudgetForLevel` 把 xhigh/max 按 high 预算处理。这些不是所有模型的通用上限；自适应 effort 模式可能完全不使用该预算表。

`buildBaseOptions` 还会按估算的剩余上下文限制输出上限，预留 4096 token 安全空间，并保持至少 1 token。预算与真正服务端 token 计数仍可能有差异。

<Diagram file="/assets/260702-ch04-thinking-levels.svg" caption="思考级别、能力与预算不是同一件事" id="260702-ch04-thinking-levels" />

### 缓存控制：偏好不是命中保证

```typescript
type CacheRetention = "none" | "short" | "long";
```

provider 将偏好映射到支持的协议。以已核对的 Anthropic 实现为例：

- none 不生成 cache_control；long 只有在 compat 支持时才加 ttl: 1h。
- system 内容、工具定义以及对话末尾合适的块可设置缓存标记。
- `convertMessages` 看的是**最后一条转换后的消息**；它为 user 或 system 时才处理末尾块，不是向前搜索“最后一条 user”。工具结果转换成 user 后也可能成为该位置。
- 工具缓存标记受 `supportsCacheControlOnTools` 控制；原生动态工具变更模式还区分初始工具与延后声明工具。

OpenAI Responses 的缓存选项同样受模型 compat 控制：当前类型包含 `supportsExplicitPromptCacheMode`，不能把所有模型的 long 一律写成固定的 `prompt_cache_retention: "24h"`。OpenAI-compatible 也不意味着默认支持 Anthropic 标记，需看 `cacheControlFormat`。

对象引用是否复用不决定缓存。请求前缀内容、能力、有效期和服务端策略才相关；不能保证“system/tools 没变就必命中”或“统一节省 90%”。成本按模型元数据及实际 usage 计算。

### 错误处理：变成事件，不等于循环不停

Anthropic 的 catch 分支会设置 errorMessage，把 stopReason 设为 error 或 aborted，发送 error 后结束流。Models 的异步准备失败也由 lazyStream 转换成错误消息。

**`agent-loop.ts` 收到 error / aborted 会结束本次运行**，不是无限重试。更高层若要重试、压缩恢复或降级，必须另有相应逻辑。事件编码只统一了错误表达，没有自动完成恢复策略。

`isContextOverflow` 也不是“空输出就判溢出”：

1. errorMessage 匹配已知溢出模式，同时排除限流等模式。
2. stop 且 input + cacheRead 超过传入的 contextWindow。
3. length 且 output 为零，input + cacheRead 达到窗口的 99% 以上。

这是启发式检测，无法识别所有服务端静默截断。它返回判断，不执行压缩或重试。

## 六、回到那一行代码

```text
Agent 的 streamFn（通常绑定 models.streamSimple）
  → Models：规范化上下文、按 provider 查找、解析认证
  → Provider：选择自己的 API 实现
  → API：统一 reasoning 映射、协议转换、请求与流式解析
  → AssistantMessageEventStream
  → Loop：根据最终消息、工具和队列决定下一步
```

值得带走的三个设计点：

1. **实例隔离**：模型目录、provider 注册与认证依赖由具体 models 集合持有。
2. **协议与供应商分离**：同一个 API 实现能被多个 provider 复用。
3. **统一语义不抹掉能力差异**：思考、缓存、工具和错误恢复都仍有适用条件。
